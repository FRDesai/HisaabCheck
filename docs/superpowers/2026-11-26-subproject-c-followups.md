State at 2026-11-27, branch `feat/subproject-c`, final verification run on head `e09f353` (counts re-measured on that commit).
Built on this branch: the Android owner app and, from sub-project D, the Business Health Report (printed to PDF from the browser; viewed only against local emulators in headless Chrome).
Verified here: 375 Kotlin core tests in 17 files on the JVM (0 failures, 0 errors, 0 skipped); 498 web unit tests in 36 files; 88 rules tests on the emulator (80 Firestore, 8 Storage); web production build; web lint (0 errors, 1 old warning in `adapters/firebaseAi.ts`); `:app:assembleDebug` with and without `google-services.json` (debug APK about 103 MB, 102,927,711 bytes without it and 102,930,227 with the example file); `:app:compileReleaseKotlin`; the shield on three sets of computer-generated bill images read by Tesseract.js, 0 private numbers sent silently in each: 64 bills (305 of 310 hidden, 5 previewed; the preview on 47 bills), 36 fresh bills (192 of 198 hidden, 3 previewed, 3 never read by OCR; the preview on 27 bills) and 30 held-out bills run once after the fix (165 of 165 hidden; the preview on 20 bills).

## Verified here, and what that does and does not prove

- The Kotlin core (`android/core`) passes the shared vectors in `shared/test-vectors` (150 privacy cases, 10 bill cases), Kotlin ports of the web unit tests, and 6,037 comparison cases generated by running the TypeScript core (shield 2,679, including the 100 real-OCR bills of both committed sets; parse 1,558; config 600; checks 1,200; about 4.4 MB of JSON). This shows the two cores agree on those inputs, on the JVM. It does not show they agree on Android: Android's regex (ICU) and text engines differ from the JVM's.
- The comparison cases have a staleness guard, committed with them: `android/core/src/test/resources/differential/manifest.json` holds the SHA-256 of the ten TypeScript sources the cases come from and of the generator, and `DifferentialManifestTest` fails until the cases are regenerated if any of those files changes. Presence checks (in the generator and in the Kotlin tests) fail if the named unusual characters (real astral characters such as U+1F600, and the fi ligature U+FB01, among others) are missing from the cases. Those files, the app's Kotlin sources and the shared vectors are declared inputs of `:core:test`, so changing any of them re-runs the tests instead of Gradle reporting them up to date.
- A core test (`MaskingAlwaysOnTest`) scans `android/app/src` and fails `:core:test` if any `parseConfig` call passes anything but the literal `true` as its second argument, or if `RemoteConfigSource` mentions `BuildConfig`.
- The Task 5 review of the Kotlin routing cascade approved it with no Critical or Important findings: there is one cloud call site; the image sent always passes the check that it is not the original when masking is on; a cancelled run cannot return a bill or reach the cloud; a bad prompt version ends in the same outcomes as on the web (checked against the TypeScript); the route-log fields match what the rules accept. This was a code review, not a run on a device.
- The app compiles and assembles into a debug APK, with and without `google-services.json`. Compiling does not show that any screen works.
- The shield was replayed on the words Tesseract.js read from computer-generated bill images (`shared/test-vectors/ocr-real.json` and `ocr-real-fresh.json`, replayed by `web/tests/core/shieldRealOcr.test.ts` and `ShieldRealOcrTest.kt`, which pin the figures; a preview counts as related only when a warning is on the number's own line):
  - first set, 64 bills, 310 private numbers: 305 hidden, 5 previewed (related), 0 sent silently; the preview on 47 bills;
  - fresh set, 36 bills from an independent re-review, 198 private numbers: 192 hidden, 3 previewed (related), 3 never read by OCR, 0 sent silently (5 before the round-3 fix); the preview on 27 bills;
  - held-out set, 30 bills generated after the fix with a new seed and run once (not committed, not tuned to), 165 private numbers: 165 hidden, 0 sent silently (5 with the previous version); the preview on 20 bills. The reviewers' stricter scoring, which also counts a visible `|` or `/` overlapping a number, gives 160 hidden, 3 previewed, 2 "leaked" with every digit hidden.
  These are synthetic images read by Tesseract.js, not photographs and not ML Kit.
- OCR sometimes drops a whole remittance-table row (3 of the 12 in the fresh set): the account number stays on the image, the shield has nothing to hide, and there is no preview unless something else on the bill raises one. Not fixed.
- The rules (Firestore 80 tests, Storage 8 tests) pass on the emulator. The emulator treats every Storage upload as a create, so the Storage "update" rule is never reached there. The deployed rules have not been tried.
- The wiring (`AppRoot.kt`) and the final fix wave's changes to the bill view model and the screens (inset handling, the "Recent bills" listener, the capture sweep) were checked by tracing the code by hand, not by running it.

## Check first on a real phone and a real Firebase project (in this order)

Set-up for all of these is in the README section "Android app".

1. **Install.** Install the debug APK. Without `google-services.json` it must show only "Firebase is not set up". With it, the sign-in screen must appear.
2. **App Check token.** Read the debug token from Logcat (the "debug secret" line comes from the SDK's documentation, not from a run) and register it in the Firebase console under App Check. Google's documentation says that until then even the cloud read is refused; confirm it.
3. **Sign-in with a test number.** Add a test phone number and fixed code in the console. Sign in with it (the reCAPTCHA page may open on a hand-installed APK). Then try a wrong code, an expired code and offline. After sign-in, check the consent screen shows and "I agree" saves (`users/{uid}` gets `consentVersion` `2026-11-v2-owner`).
4. **Link.** Make an invite code on the web ("Invite owner"). Type it on the phone. Check the home screen shows the shop name. Try the same code again from another phone (must say it is used or old), and a code older than 7 days.
5. **A clean bill.** Photograph a sharp bill on a phone without on-device AI. Check Processing, then the result with fields and checks, then "Done". Check the camera permission works without any CAMERA entry in the manifest (the app uses the system camera app through a FileProvider).
6. **A blurry bill.** Check the cascade ends in the preview or in manual entry as expected, and the failure screen's "Try again" re-runs the same photo.
7. **The preview.** Check it appears when the shield is unsure, that Back means "keep on this phone", and that "Send" sends. Check that nothing but the redacted image is ever shown.
8. **The redacted image.** Check every private number on the test bill is blacked out in the image that goes to the cloud and in the stored photo (if the shop stores images). Check ML Kit word boxes line up with the painted image (boxes and image scale, rotation and EXIF). Also photograph a two-column bill with bank details: ML Kit returns lines per text block, so a label and its value in another column may not be on adjacent lines; see how it groups them and how often the preview appears (it may appear more often than on the web).
9. **The bill in the web inbox and its route log.** Open the web inbox as the CA: the bill must show, with the right path (device or cloud) and fields. Open the dashboard: the route log must show platform `android`, counts and types only. This also proves the real rules accept the Android write shapes (route-log field types, the full-extraction update, the late `imagePath`).
10. **On-device path on a supported phone** (Galaxy S25/S26 families, Pixel 9/10/11). Check the model download flow and progress, and a bill read on the device. Confirm the on-device adapter's answers are marked as coming from the device (`inferenceSource`): the adapter rejects an answer that is not, so if the marker is never set every on-device read will be refused and fall to the cloud.
11. **Timeout and cancel.** Confirm the 8-second device timeout and Back or "Done" during Processing really stop the device and cloud adapters (the cascade relies on the adapters' suspending calls being cancellable).
12. **Offline save.** Take a bill with the connection off. The result must not hang (writes wait at most 15 seconds and then say the change is queued), the bill must appear on the CA's side once the connection returns, and a bill the CA reviewed in the meantime must be refused with the "already reviewed" message.
13. **Rotation and process death.** Rotate on each screen (a running bill must continue). With the camera open, let the system kill the app's process (for example with "Don't keep activities" on in the developer options, or `adb shell am kill com.hisaabcheck.app` while the camera is in front), take the photo, and check the home screen receives it and the bill is read (the capture must not be deleted first).
14. **Sign out.** Sign out during Processing: the bill must stop. Sign out and sign in again to the same shop, add a bill, and watch "Recent bills" update. Sign in as an owner of a different shop: bills must go to the new shop, and the old shop's list must not show.
15. **Core on Android.** Replay the differential fixtures (`android/core/src/test/resources/differential`) and the shared vectors in an instrumented test on a device or emulator. All core proofs ran on the JVM.
16. **Storage overwrite behaviour in production.** Check whether a CA's replacement of a stored photo is judged as an update or a create by the real Storage service (the rules are written to pass either way), and that an owner cannot overwrite a stored photo.
17. **App Check enforcement.** Turn on App Check enforcement for Firestore and Storage in the console (it is a deploy-time setting, not in the rules), then repeat steps 3 to 9 with it on.
18. **Camera photo sizes.** Check the stored JPEG stays under the 3 MB Storage rule (the image is scaled to at most 1600 px on the longest side).
19. **Retry cloud and the stored photo.** In a shop that stores photos, make the cloud read fail (for example offline after the preview), tap "Retry cloud", black out one more number in the second preview and send. Then open the bill as the CA on the web and check the photo shown is the second one, with the extra box. Repeat on a slow connection so the first upload is still running when the second is sent.
20. **Screens on Android 15 or later.** On every screen, check nothing is drawn under the status bar, the navigation bar or a display cutout, that the last button of each scrolling screen can be reached, and that the keyboard does not cover the field being typed in (sign-in, link and the result screen), with no doubled gap above the keyboard.

## Decisions made during the build

- The owner's consent has its own wording and its own version string, `2026-11-v2-owner` (the web's consent version is separate). The owner wording says the CA can see the bills and gives the way to withdraw (sign out and ask the CA to delete the data).
- An invite code works for 7 days and for one owner. Linking checks that the invite document names this shop and this shop's CA and is under 7 days old.
- A CA can only unlink an owner, and must replace or remove the invite code in the same write, so the old code cannot link again. The web has no unlink button yet.
- A shop is never created with an owner. Only the owner's own link write can name one.
- The owner can create bills, and can edit bills that are draft or manual entry. Owners cannot change a reviewed bill, and cannot approve, reject, reopen or delete. An owner's bill never carries review fields.
- Storage: the shop's CA or its linked owner can read; the owner can only add a photo where none exists; replacing and deleting are the CA's.
- On Android, masking cannot be turned off in any build: the app always reads Remote Config with masking forced on, so a `mask_pii` of `false` in the console has no effect there (the installable APK is a debug build). On the web it is forced on in production builds.
- Each save stores its photo under a new name, `shops/{shopId}/bills/{billId}-{suffix}.jpg` (the suffix is the time in milliseconds in base 36), and `imagePath` points to that name. A retry never depends on or falls back to an earlier attempt's photo, and only the newest attempt for a bill may write `imagePath`: an earlier attempt's upload that finishes late (for example on a poor connection) is not linked and reports "Photo not stored", as does a failed upload or `imagePath` write. Marking the newest attempt and queueing its bill write happen under one lock, so a late link is either queued before the newer full write (which clears it) or not made. This state is in memory only; an upload does not survive a process death.
- Android route logs are written by the shop's linked owner, with `platform` `android` and the shop's `caUid`, so the log shows on that CA's dashboard.
- `compileSdk` is 37.1 (the Compose version in use needs it), so the platform package `android-37.1` must be installed on any build machine. Lifecycle 2.11.1 and coroutines 1.11.0 were used. The Gradle 9.6.0 zip was fetched with `curl` because Java could not reach the download host.
- Gradle runs only through `android/gw`, which lets one build run at a time (repo-local lock `android/.gradle/gw.lock`, with takeover of a lock left by a dead process). It adds `--console=plain` itself.
- The default cloud model is `gemini-3.5-flash-lite` on both platforms (it was `gemini-3.1-flash-lite` on the web before this work).
- The cloud adapter sends the redacted JPEG bytes unchanged as inline data, decoded and handled off the main thread. The original photo bytes never leave the routing cascade.
- The Kotlin core uses its own strict JSON parser for the model's answer, and avoids `\b \d \w \s` and flags in regular expressions, because Android's regex engine treats them as Unicode-aware.
- In the router, `catch` blocks catch `Exception`, not `Error` (an out-of-memory error ends in the failure screen and sends nothing). A device timeout of 0 or less skips the device call. A device read that times out is cancelled (the web leaves it running). A still-running OCR is cancelled on the device-pass exit. The cloud call gets a fresh image input built from the bytes to send.
- Sign-in has a 70-second watchdog so a lost callback cannot leave the owner stuck on "busy". Writes to Firestore wait at most 15 seconds for the server and then say "No connection"; a queued write may still land later, and the link step copes with that.
- The shop lookup after sign-in asks the server first and falls back to the cache. If working out the account fails (for example offline with an empty cache), the app stays on a loading screen that shows the message, "Try again" and "Sign out".
- The bill flow shows the failure screen through the home screen, adds a "Black out bottom third" button (as on the web), and the result screen's Save waits at most 15 seconds before saying the change is queued. The refusal message ("your CA has already reviewed this bill") waits for the bill's own save to answer, for at most 10 seconds, then shows a neutral connection message.
- Wiring (this task): the bill view model is keyed by shop id and held by the activity; Back on Result, Failed and Processing calls `done()` (on Processing that cancels the bill, with no confirmation); the preview handles its own Back as "keep"; sign-out calls `done()` first; and whenever the bill screen leaves composition for any reason other than a rotation, `done()` is called, so a session that ends by itself also stops the bill and drops the photo. The "Recent bills" listener is started when the bill screen is entered (a no-op if it is running) and removed, with the list cleared, when it leaves for any reason other than a rotation; a listener error marks it stopped so the next entry starts it again.
- The camera capture folder is swept at start and on "Done", but only of files last changed more than 10 minutes ago, so a photo taken while the app's process was killed behind the camera is still there to be read.
- The app draws edge to edge and insets all content once, at the root (system bars, display cutout and keyboard).
- No CAMERA permission is declared; photos come from the system camera app through a FileProvider.
- The on-device model calls use the SDK's deprecated `checkStatus` and `download` (deprecated in 16.0.0-beta08); the replacement is `GenerativeModel.onDeviceExtension`.
- The differential fixtures (about 4.3 MB of JSON) are committed so the Kotlin tests need no Node; regenerating them needs `web/node_modules`.

## Known gaps (small, deferred)

Privacy shield (web and Kotlin cores)
- Remaining leak paths: a number OCR did not read at all (a dropped table row) is not hidden or flagged; a PAN or IFSC whose shape OCR has misread too far is previewed, not hidden; digits misread as letters inside a number can keep it from being hidden (previewed only at low confidence); a dot or time inserted by OCR inside a number (`98450123.45`, `50100 12:30 4567`, `5010 0234.56 78`), a bare 8-digit local landline (`2345 6789`) and `(080) 2345.6789` pass without a warning; a wrong read with high confidence is not flagged.
- The preview appears on most bills (47 of 64, 27 of 36, 20 of 30 generated bills). Any unclaimed run of 9 or more digits is hidden, so e-way bill numbers, acknowledgement numbers and barcodes are hidden too (the e-way number on all 64 bills of the first set). A two-group number with a decimal tail (`50100234 5678.00`) asks for the preview, and so does an HSN code next to an amount whose commas OCR dropped (`61369305 5787.00`): the two cannot be told apart.
- Usability change declined: digits glued to letters still count towards the long-digit-run warning, because excluding them could turn a previewed account number into a silent leak.

Rules
- Deleting an invite document while its code is still on the shop lets another CA create that same code for their own shop.
- An owner's draft updates are not restricted to particular keys, only kept free of review keys.
- Owner writes are loosely bounded inside their own shop: extra keys on drafts, and any number of route logs and stored JPEGs.
- A late `imagePath` write from an owner is refused if the CA reviewed the bill meanwhile, which leaves the photo stored but unlinked.
- Old invite documents pile up when "New code" replaces them.
- The `exists()` check in the link rule is redundant.
- Test (d) `{ownerUid: null}` guards a combination of rules and does not isolate one.
- The Storage "update" rule is untested (the emulator never reaches it), and production overwrite behaviour is unconfirmed.
- Enforcing App Check on Firestore and Storage is a console setting that has not been turned on.

Web
- The web shows no "expired" note on an old invite code.
- An owner who signs in to the web app gets the CA screens with an empty shop list.
- The web has no button to unlink an owner.
- The web's offline-cache guard stores the last signed-in uid in localStorage; a first sign-in with no stored uid is trusted (a cache left by a build from before the guard is not wiped). A wipe blocked by another open tab, or a second automatic reload in one page session, signs the user out with a message on the login page. Signing out waits 5 seconds for queued changes and then asks "Stay signed in" or "Sign out anyway"; a session that ends by itself loses its queued changes when the next user's sign-in wipes the cache.

Core
- Words on a negative OCR line are never scanned by either shield (a guard upstream on both platforms).
- A prompt version named like an `Object.prototype` property (for example "toString") makes the prompt builders throw in both cores; the router must catch it as the web does.
- Neither shield treats non-ASCII digits (full-width, Devanagari) as digits, which matters if OCR outputs them.
- The shared vectors have no Unicode-space cases.
- `JsSemantics.kt` sits in `shield/` but is used across the core.
- The JSON parser lives inside `Parse.kt`.
- `gstinStateCode` returns a `Double`, to keep JavaScript number semantics.
- A NaN box passes through redaction planning, on both sides.
- A throwing step callback inside the device read becomes `device_error`, as in the web router, and the callback for `done` can then fire twice.
- If the prompt lookup throws on the cloud step, the result is `cloud_error` with a cost of 0.0003 although no call was made (same in the web).
- Timeout and cancellation work only if the adapters use cancellable suspending calls; this is unchecked on a device.
- If the caller cancels during the short wait after the "done" step, the router throws a cancellation after reporting done (harmless in the app).
- The differential fixtures are single-line JSON, so each regeneration re-commits about 4.3 MB.
- In one generated case a random insert splits a surrogate pair (the case holds a lone surrogate).
- The mis-escape replay test covers two of the seven named unusual characters (U+1F600 and U+FB01).
- The cascade's single catch guards are not individually testable; one guarded step function is the backstop.
- One cancellation test lacks two assertions (that the original bytes never reach the cloud and that no step is reported).
- There is no test for cancellation at the exact instant the device timer fires.
- The device-pass exit waits for the OCR decode to finish before returning (the latency is measured before that wait).
- A backwards clock jump makes the measured time negative, and the rules would refuse that route log (same on the web).
- JVM `Error`s from adapters are not caught.
- A device timeout of zero or less skips the device call (the web lets an instant answer win; the app never sets it).

Adapters
- The helper that waits for a Google task (`awaitTask`) is copied in four files (three adapters and the session).
- Bitmaps are never recycled.
- The text recogniser is never closed.
- The on-device model has no response MIME type set.
- `download()` throws if the SDK emits nothing for a model that is already available, so callers must call it only when the model is downloadable or downloading.
- `DownloadFailed.exception`'s type is not on the app's classpath, so the on-device adapter throws its own error for a failed download.
- ML Kit lines are per text block, so a label and its value in another column can be on non-adjacent lines and the preview will appear more often than on the web.
- The `onStep` hook hops through the main dispatcher.
- Remote Config is fetched before every bill, with a 3.5-second cap.
- Cancellation of the on-device call is expected but unproven.
- `ImageLoader` uses `BitmapFactory` with `ExifInterface` instead of `ImageDecoder` (deliberate).
- Imports in the adapter files are not in order.

Screens
- The screens collect state with `collectAsState`, not the lifecycle-aware version.
- An owner linked to several shops gets an arbitrary one.
- TalkBack reads the consent bullets as separate symbols.
- When a server permission error comes with an empty cache, the shop lookup reports "No connection".
- A verification code that arrives after "Change number" can still be accepted into the state.
- The shop lookup after sign-in has no timeout of its own and relies on Firestore's offline detection.
- A link write that timed out offline can still land later (the rules bound what it can do).
- There is no "Retry save" without re-running the whole read.
- The recent-bills list groups digits in the Western way, not the Indian way.
- Turning a non-finite number into form text is not guarded.
- "Retry cloud" saves with a full write and can overwrite an edit that is still queued locally.
- An abandoned run could still make a cloud call with the redacted image if the core ignored cancellation.
- The order of step updates depends on the core calling them from one coroutine.
- The wording shown after the app was recreated by the system is not tailored to it.
- If the caller is cancelled while a capture file is being created, a 0-byte file is left until a sweep at the next start or "Done" finds it more than 10 minutes old.
- A cancelled "saved" signal would leave the edit state at "Saving".
- The neutral connection message after 10 seconds is not revisited if the save settles later.
- `done()` runs twice on sign-out from Home (harmless).
- If the session ends during a configuration change, the bill view model keeps its photo until the activity is destroyed.
- The Android cache wipe and the "Sign out anyway" dialog have never run on a phone. The wipe starts when the signed-out screen is shown (also after a session that ended by itself), waits at most 5 seconds per step, and a failed or timed-out wipe is ignored and tried again at the next session end or app start. Signing out first waits 5 seconds for queued offline changes; if any remain, the owner chooses "Stay signed in" or "Sign out anyway" (which loses them). Check step 14 with two owners on one phone, once offline.
- The shop's settings (such as "store images") are cached for the session.
- After "Retry cloud", the earlier attempt's stored photo (including one whose upload finished late and was not linked) stays in Storage, unreferenced; owners cannot delete, so cleanup is the CA's side.
- "Retry cloud" stays available after the owner has saved edits, and its save still overwrites those edits.
- Consent wording (both platforms), changed 2026-11-27: the old sentence "Data is kept in India (Mumbai)" was not something the code guarantees for the cloud read through the Gemini Developer API. Both screens now say "Saved bill data is stored in India (Mumbai). Bills read in the cloud are processed by Google's Gemini service." and the versions are `2026-11-v2` (web) and `2026-11-v2-owner` (Android), so existing users are asked again. Not checked: where Google processes a cloud read.

Build
- The app module has no test dependencies.
- `kotlinx-serialization-json` is an implementation dependency of the core, not an API one.
- There is no dark window theme (the Compose theme follows the system, the window behind it does not).
- `gw` has a microsecond race at lock takeover that can let two builds overlap briefly.
- A `gw` killed with SIGKILL leaves its `gradlew` running.
- Running `gw` through a symlink resolves to the symlink's directory.
- Release builds were compiled but never assembled; R8 and minify are not configured.
- The Gradle wrapper has no checksum (`distributionSha256Sum` is not set).
